最后核验日期：2026-07-29

## 一、两个工具，能力不对称（决定检索顺序）

| | `case-keyword`（`get_case_list`） | `case-semantic`（`search_case`） |
|---|---|---|
| 入参主力 | `title` / `fulltext`（**至少一个**） | `text`（自然语言案情） |
| **参照级别筛选** | ✅ `caseGrade` 数组 | ❌ **无** |
| **法院层级筛选** | ✅ `court`（最高／高级／中级／基层人民法院） | ⚠️ 只能按具体法院名或省份 |
| 地域筛选 | 无（靠 `court` 或关键词） | ✅ `province`（省份全称）／`name`（法院全称） |
| 日期筛选 | `startLastInstanceDate` / `endLastInstanceDate`（**点号** `2024.1.1`，审结日期） | `date_start` / `date_end`（**ISO** `2024-01-01`） |
| 文书类型 | `documentAttr` 数组 | `type` 单值 |
| 返回 | 包裹对象 `{Message, Data[], Total}`，约 29 字段 | **裸数组**；空结果为 `{"result":[]}` |
| **返回 `CaseGrade`** | ✅ 有 | ❌ **没有** |
| 返回争议焦点 | ✅ `ControversialFocus` | ❌ 无对应字段 |
| 返回裁判依据 | ✅ `RefereeBasis` | ❌ 无对应字段 |
| 链接字段 | `Url`，**markdown** `[北大法宝](…?way=mcp)`，取括号内裸链 | `url`，纯链接 |

### 由此得出的两条硬性操作规则

**规则 1：第四条的四顺位筛选必须走 `case-keyword`。**

因为顺位一（指导性案例）、顺位二（典型案例）依赖 `caseGrade` 筛选，顺位三、四依赖 `court` 层级筛选，而**语义检索这两个筛选都没有**。用语义检索去做顺位检索，只能靠运气。

**规则 2：语义检索命中的案子，效力级别一律缺失，必须回补。**

`search_case` 不返回 `CaseGrade`。处置：拿到案号或标题后，用 `case-keyword` 以 `title` 或 `fulltext` 回查一次补取该字段。**回补不成功的，效力表述只能写"效力待核"，不得按法院层级推断**（见 [statutory-structure.md](./statutory-structure.md) 第九节）。

**语义检索的正确位置**：用在第 1 步"焦点还没收敛、不知道该用什么关键词"的探路阶段，以及关键词 0 命中后的兜底。**不要用它替代顺位检索。**

## 二、第五条三种法定方法，逐项对照能不能做

> "五、类案检索可以采用关键词检索、法条关联案件检索、案例关联检索等方法。"

| 法定方法 | 法宝 MCP 能否直接实现 | 落地做法 |
|---|---|---|
| **关键词检索** | ✅ 原生支持 | `get_case_list` 的 `title` / `fulltext` |
| **法条关联案件检索** | ❌ **无专用接口** | 近似实现，见下 |
| **案例关联检索** | ❌ **无专用接口** | 近似实现，见下 |

**这是必须如实写进报告的能力缺口**，不是可以含糊过去的地方——第八条要求披露检索方法，用近似手段实现的就要说明是近似手段。

### 法条关联案件检索的近似做法

真正的法条关联检索是"给一个条文，返回所有引用该条文裁判的案件"。法宝 MCP 没有这个入口。两步近似：

1. 用 `fatiao`（`get_law_item_content`）或 `law-search-service.get_article` 取回**条文原文**，确认条号与内容一致（防止张冠李戴）。
2. 把**法规简称 + 条号**作为 `fulltext` 传给 `get_case_list`，例如 `fulltext=劳动合同法第四十条`。判决书的"裁判依据"部分通常会出现该表述。

**局限必须写明**：这是**全文关键词匹配**，不是引证关系检索。它会漏掉只写"依照《中华人民共和国劳动合同法》相关规定"而不写具体条号的判决，也会误收只在当事人主张里提到该条的判决。

**校验手段**：命中后看返回的 `RefereeBasis`（裁判依据）字段里是否真的含该条文——**如果只出现在 `Ascertain`（查明）或当事人主张部分，不能算法条关联命中**。

### 案例关联检索的近似做法

真正的案例关联检索是"给一个案件，返回其上下级审、再审、被引用情况"。同样没有专用接口。近似：

- **查上下级审／是否被改判**：以**主要当事人名称**作为 `fulltext`，配合 `court` 提高一级层级、放宽日期区间检索。这同时就是第 5 步核验第 1、2 项的执行手段。
- **查是否被取代**：指导性案例被新指导性案例取代的情形，以争议焦点关键词 + `caseGrade=["指导性案例"]` 重检一轮，看有无更晚发布的同主题案例。

**局限**：当事人为自然人时常被匿名化处理（如"张某"），此路径可能失效。失效时该案标 `[生效性待核]`，不要因为查不到就默认它有效。

## 三、四顺位的具体检索式

顺位定义见 [statutory-structure.md](./statutory-structure.md) 第二节。**按序执行。**

### 顺位一：指导性案例（不受"近三年"限制）

```
工具：case-keyword (get_case_list)
参数：fulltext=[争议焦点核心词]  caseGrade=["指导性案例"]
     不设日期筛选 —— 第四条明确"除指导性案例以外"才优先近三年
```

**这一轮必须单独跑，且必须跑。** 理由是第十条的程序效果：提交指导性案例能强制法院在裁判文书说理中回应。**哪怕相似度不是最高也要找出来。**

命中后逐条核第九条的两项例外（是否与新法冲突、是否被新指导性案例取代）。

### 顺位二：最高人民法院典型案例及生效裁判

```
工具：case-keyword
参数：fulltext=[核心词]  caseGrade=["典型案例","公报案例","参考案例"]
     court=最高人民法院
     startLastInstanceDate=[今年-3].1.1
```

`caseGrade` 的可选值（当次 schema）：`指导性案例, 参考案例, 公报案例, 典型案例, 参阅案例, 评析案例, 优秀案例, 经典案例, 应用案例, 法宝推荐, 普通案例`。

**注意 `法宝推荐` 是数据库的编辑标记，不是官方参照级别**——可以用它辅助筛选，但**报告里不得把它作为效力依据表述**。同理，`优秀案例`、`经典案例`、`应用案例`、`评析案例` 均非法发〔2020〕24 号第九条意义上的效力类别，一律按"可以参考"处理。

### 顺位三：本省高院参考性案例及生效裁判

```
工具：case-keyword
参数：fulltext=[核心词]  court=高级人民法院
     startLastInstanceDate=[今年-3].1.1
```

`court` 只能筛层级，筛不出具体是哪个省的高院。**两种补法**：把省份并入 `fulltext`，或改用 `case-semantic` 的 `province`（省份全称）然后按上文规则 2 回补 `CaseGrade`。

**"本省"按受理法院所在省确定**，不是当事人所在地。

### 顺位四：上一级法院及本院生效裁判

```
工具：case-keyword
参数：fulltext=[核心词]  court=中级人民法院 或 基层人民法院
     startLastInstanceDate=[今年-3].1.1
```

需要知道受理法院层级才能确定"上一级"是哪一级——这是第 1 步必须问到受理法院的原因。

### 停止规则

前一顺位已检到适格类案时，**可以**停止后续顺位，但必须在报告里写明：

> 依第四条"已经在前一顺位中检索到类案的，可以不再进行检索"，本次检索至顺位 [N] 停止。

**不写就等于检索不全。** 律所版通常仍建议往下检——对方也会检索。

## 四、检索式记录格式（第八条"检索方法"要素的实质）

每一轮检索**执行前写下、执行后补齐**，原样进报告：

```
顺位 [1-4] · 方法 [关键词 / 法条关联（近似）/ 案例关联（近似）/ 语义（第五条"等方法"）]
工具 [case-keyword | case-semantic]
参数 title=…  fulltext=…  caseGrade=[…]  court=…  日期区间=…
命中 本次返回 [N] 条 ｜ 实读 [M] 条 ｜ 判定为类案 [K] 条 ｜ 排除 [N-K] 条
```

**没有这一段，报告不可复现，也就不满足第八条。**

## 五、三个必须避开的表述陷阱

### 1. `Total` 不是"共找到 N 条类案"

列表类接口返回的 `Total` 是**全库命中总数**，可达千万级，不是本次返回条数（返回前 20 条）。

- ❌ "共检索到 3,847 件类案"
- ✅ "本次返回 20 条，全库命中量较大（`Total`=3,847），已通过增加 [某条件] 缩小范围"

**把 `Total` 写成类案数量，是一句会立刻被内行看穿的话**，而且它同时虚报了工作量和检索精度。

### 2. 裁判要点只能从"本院认为"提

`get_case_list` 返回的字段里，只有 **`Identified`（本院认为）** 是法院的裁判理由。

| 字段 | 是什么 | 能否作为裁判要点来源 |
|---|---|---|
| `Identified` | 本院认为 | ✅ **唯一来源** |
| `ControversialFocus` | 争议焦点 | ✅ 可用于比对表的"争议焦点"列 |
| `RefereeBasis` | 裁判依据 | ✅ 可用于校验法条关联 |
| `RefereeResult` | 裁判结果 | ✅ 可用于结果列 |
| `Ascertain` | 本院查明 | ⚠️ 事实，**不是**裁判理由 |

从 `Ascertain` 或当事人主张部分提取"裁判要点"，是 guardrails 第三节点名的那类错误——**引注真实存在，但该段落不支撑该命题**。

### 3. 案号要原样抄，不要重排

案号格式复杂（`（2020）沪 02 民终 8503 号`、`（2013）浦民一（民）初字第 31722 号`），全角半角、汉字数字混排。**从 `CaseFlag` 字段原样抄。** 拿不准真伪时用 `case-number`（`anhao_recognition`）核一遍。

**编造案号是本域最容易发生、也最容易被抓住的幻觉。** MCP 不可用时**不得**凭记忆列举案号——见 SKILL.md 的降级表。

## 六、schema drift：参数名可能被拒

`docs/references/pkulaw-mcp.md` 记录过：部分部署下 `tools/list` 广告的参数名会被后端拒绝，报 `Unexpected keyword argument`。

**已观察到的两组名字，在不同部署下互为"正确"：**

| A 组 | B 组 |
|---|---|
| `province` | `courthouse_province` |
| `date_start` / `date_end` | `decision_date_start` / `decision_date_end` |
| `type` | `doc_type` |
| `name` | `courthouse_name` |
| `department` | `issue_department` |

**处置顺序**：

1. 先用**当次 `tools/list` 广告的名字**（本次会话广告的是 A 组）。
2. 被拒则换另一组重试一次。
3. **两组都被拒：去掉该筛选，把条件并入主检索文本**（如把"上海"写进 `fulltext`），**不放弃检索**。
4. 在报告的检索式记录里注明"该筛选参数被后端拒绝，已改为文本内条件"——这影响检索精度，属于必须披露的信息。

## 七、错误码处置（账户状态类禁止改词重试）

| 码 | 含义 | 处置 |
|----|------|------|
| `90001` | 积分用尽 | 「检索积分已用尽，请充值/续费后再试。」**不重试** |
| `90002` | 成员用量达上限 | 「成员用量已达上限，请联系管理员提配额。」**不重试** |
| `900908` | 无该服务权限 | 「未开通该服务，请在 mcp.pkulaw.com 确认订阅。」**不重试** |
| `401` / `403` | 未授权 | 在客户端重新授权/连接，确认已订阅后再试 |
| 未列出的码 | — | 如实说"服务暂时不可用"，**不要编造检索结果** |

**账户状态类错误改词重试没有意义，只会消耗用户时间。**

另外实测中出现过**单次调用偶发失败**（`Streamable HTTP error`）与**返回全空字段**：这两种是可以重试的，重试一次即可，且**标题用半角括号（如 `(试行)`）比全角更稳**。**返回全空不等于该条不存在**——不要据此断言"无此条文"。
